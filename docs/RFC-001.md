## 1. Contexto

O iGRP é um framework interno do NOSI com arquitetura de microserviços em Spring Boot.

| Peça | Responsabilidade |
|---|---|
| IDP federado (Keycloak, Auth0 ou outro, configurável) | Autenticação. Confirma quem é a pessoa e mais nada. |
| Serviço central de autorização (Spring Boot) | Roles, permissões e aplicações. Liga-se ao IDP. |
| Spring Security com OAuth2 | Valida tokens em cada microserviço (Resource Server). |

Princípio de partida: **o IDP autentica, o serviço central autoriza**. Não há permissões no IDP. Com esta separação, troca-se de fornecedor de identidade sem mexer no modelo de permissões. Todo o desenho que se segue assenta nela.

## 2. Problema

O modelo em produção (modelo 1) embutia todas as roles e permissões no JWT emitido pelo central.

Exemplo ilustrativo do payload no modelo 1:

```json
{
  "sub": "8f2c…a91",
  "email": "joao@nosi.cv",
  "roles": ["ADMIN_FAT", "TEC_RH", "…"],
  "permissions": [
    "faturas.list", "faturas.read",
    "faturas.create", "faturas.update",
    "clientes.read", "pagamentos.list",
    "… centenas de entradas …"
  ]
}
```

Consequências:

- **Tamanho.** Com o crescimento do número de permissões, o token tornou-se enorme e o Ingress passou a rejeitar pedidos com `Header too large`. Subir o limite do Ingress só adia o problema.
- **Frescura.** As permissões ficam congeladas até o token expirar. Uma revogação não tem efeito imediato.

## 3. Objetivos e não-objetivos

**Objetivos**

- Token de tamanho constante, independente do número de permissões.
- Revogação de permissões com efeito no pedido seguinte.
- O serviço central não pode ser gargalo nem ponto único de falha chamado em cada pedido por todos os microserviços.
- Nenhum microserviço implementa segurança: herda-a de uma dependência partilhada.
- Permissões geridas em runtime, como dados, sem recompilar nem redistribuir serviços.
- Fechado por omissão: uma rota só é pública se alguém a marcar como tal.
- Um modelo único para pessoas, serviços e agentes.
- Prova de auditoria que não depende de sistemas externos.

**Não-objetivos**

- Motor de autorização baseado em relações (Zanzibar/ReBAC). Ver 8.1.
- Mini-linguagem própria de regras de visibilidade. Adiada, ver 8.3.
- Descoberta automática das APIs que uma página chama. Adiada, ver 9.4.
- Distribuição do starter (Nexus ou Artifactory interno): ficou fora do âmbito do debate.

## 5. Permissões em runtime

### 5.1 Modelo 1 contra modelo 2

| Critério | Modelo 1 · no token | Modelo 2 · por pedido |
|---|---|---|
| Como funciona | O central emite um JWT enriquecido com roles e permissões | Token magro; as permissões são carregadas a cada pedido |
| Latência | Nenhuma chamada extra | Uma consulta por pedido, mitigada com cache |
| Frescura | Congelada até o token expirar | Revogação imediata possível |
| Tamanho | Cresce com as permissões e quebra o Ingress | Constante e pequeno |
| Estado | Em produção hoje | **Escolhido** |

> **Decisão D1.** Migrar para o modelo 2, sem que todos os microserviços apontem diretamente para o serviço central.

Payload do JWT no modelo 2 (ilustrativo):

```json
{
  "sub": "8f2c…a91",
  "email": "joao@nosi.cv",
  "iat": 1760430000,
  "exp": 1760433600
}
```

As permissões passam a viver no Redis: `SMEMBERS permissions:user:8f2c…a91`.

### 5.2 Como evitar sobrecarregar o central

| Proposta | Avaliação | Estado |
|---|---|---|
| Cache distribuído em Redis | Chave `permissions:user:{id}`. O microserviço lê do Redis e só chama o central quando a chave falta. | **Escolhida** |
| Permissões por âmbito do serviço | Cada serviço carrega só as permissões que lhe dizem respeito. Reduz o tamanho mas não resolve o problema. | Rejeitada |
| Cache local com eventos | Memória em cada serviço, invalidada por Kafka ou RabbitMQ. Mais peças e risco de inconsistência entre réplicas. | Rejeitada |

> **Decisão D2.** Cache distribuído em Redis, partilhado por todos os microserviços, padrão cache-aside.

**Modelo de dados no Redis**

| Elemento | Valor |
|---|---|
| Chave | `permissions:user:{id}`, onde `{id}` é o `sub` do token |
| Tipo | Set |
| Membros | Chaves de permissão (`faturas.read`, `faturas.list`, …) |
| Expiração | TTL, ver 5.3 |

**Fluxo por pedido**

1. O pedido chega com `Authorization: Bearer …`.
2. O Resource Server valida o token e extrai o `sub`.
3. O starter lê `permissions:user:{sub}` do Redis.
4. **Hit** (a maioria dos pedidos): popula as authorities do contexto de segurança.
5. **Miss** (a chave expirou ou foi invalidada): faz GET ao serviço central, grava com `SADD` + `EXPIRE`, popula as authorities.

Código ilustrativo (injeção de dependências e tratamento de erros omitidos; as duas classes vivem no starter, nunca nos microserviços):

```java
@Service
class PermissionCacheService {
  Set<String> permissions(String userId) {
    var key = "permissions:user:" + userId;
    var hit = redis.opsForSet().members(key);
    if (hit != null && !hit.isEmpty())
      return hit;                                    // hit
    var perms = central.permissions(userId);
    redis.opsForSet().add(key, perms.toArray(String[]::new));
    redis.expire(key, props.ttl());
    return perms;                                    // miss
  }
}
```

```java
class IgrpJwtConverter implements Converter<Jwt, AbstractAuthenticationToken> {
  public AbstractAuthenticationToken convert(Jwt jwt) {
    var auths = cache.permissions(jwt.getSubject())
        .stream()
        .map(SimpleGrantedAuthority::new)
        .toList();
    return new JwtAuthenticationToken(jwt, auths, jwt.getSubject());
  }
}
```

### 5.3 TTL e invalidação

| Proposta | Avaliação | Estado |
|---|---|---|
| TTL curto (≈5 min), sem invalidação | Frescura aceitável sem mecanismo extra, mas multiplica as chamadas ao central | Rejeitada |
| TTL longo + invalidação ativa pelo central | O TTL passa a rede de segurança para eventos de invalidação perdidos | **Escolhida** |

> **Decisão D3.** TTL entre **30 e 60 minutos**. O exemplo usa `45m`; o valor final fica por fixar (Q1).
>
> **Decisão D4.** Sempre que altera roles ou permissões de um utilizador, o serviço central apaga `permissions:user:{id}`. O pedido seguinte, em qualquer microserviço, recarrega os dados novos. Como todos partilham o mesmo Redis, uma remoção chega a todos.

Sequência:

1. O gestor muda as roles do João no painel.
2. O central grava e faz commit.
3. O central executa `DEL permissions:user:joao`.
4. Próximo pedido do João: miss.
5. Recarrega do central e grava com TTL.

```java
@Transactional
void assignRole(UUID user, UUID role) {
  userRoles.save(new UserRole(user, role));
  afterCommit(() -> redis.delete("permissions:user:" + user));
}
```

`afterCommit` representa um `TransactionSynchronization` ou um `@TransactionalEventListener(phase = AFTER_COMMIT)`.

```yaml
igrp:
  security:
    cache:
      ttl: 45m   # 30–60 min
```

> **Alerta A1. Invalidar depois do commit.** Se a chave for apagada antes do commit, um pedido concorrente pode recarregar as permissões antigas e gravá-las de novo no Redis.
>
> **Alerta A2.** TTL curto sem invalidação multiplica as chamadas ao central. Não usar como substituto da invalidação.

## 6. O `igrp-security-starter`

> **Decisão D5.** Toda a segurança dos microserviços vem de um starter Spring Boot partilhado. Segurança herdada, não implementada. Um bug corrige-se num sítio e sobe-se a versão.

### 6.1 Conteúdo

- `PermissionCacheService` (Redis).
- `JwtAuthenticationConverter` customizado (`IgrpJwtConverter`).
- Cliente HTTP do serviço central (WebClient ou Feign; escolha em aberto, Q2).
- `@ConfigurationProperties`: URL do central, Redis, TTL, rotas públicas.
- `SecurityFilterChain` com `oauth2ResourceServer`.
- `RouteAuthorizationFilter` e `PermissionKeyResolver` (secção 7).
- Anotações `@Permission` e `@Public`.
- `RouteRegistrar` (registo de rotas no arranque).
- `AuditLogger` (secção 11).

### 6.3 Autoconfiguração

```java
@AutoConfiguration
@EnableConfigurationProperties(IgrpSecurityProperties.class)
public class IgrpSecurityAutoConfiguration {

  @Bean @ConditionalOnMissingBean
  PermissionCacheService permissionCache(…) { … }

  @Bean @ConditionalOnMissingBean
  IgrpJwtConverter jwtConverter(PermissionCacheService c) { … }

  @Bean @ConditionalOnMissingBean
  SecurityFilterChain igrpChain(HttpSecurity http, …) {
    return http
      .oauth2ResourceServer(o -> o.jwt(j ->
          j.jwtAuthenticationConverter(jwtConverter)))
      .addFilterAfter(routeFilter, BearerTokenAuthenticationFilter.class)
      .build();
  }
}
```

Ficheiro `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, uma classe por linha, nome completo numa só linha:

```
cv.nosi.igrp.security.autoconfigure.IgrpSecurityAutoConfiguration
```

- `@ConditionalOnMissingBean` deixa uma porta para uma customização excecional sem partir nada. Na prática nenhum microserviço define estes beans.

> **Alerta A3.** Sem o ficheiro `AutoConfiguration.imports`, o Spring Boot não descobre a configuração do starter e nada é carregado. É o detalhe mais esquecido.

### 6.5 Endpoints do serviço central

Todos os caminhos em inglês, alinhados com os que o Access Management já expõe
(`/api/applications`, `/api/users`, `/api/authorize/check`). O **contrato** de cada um — corpo,
erros, autenticação — é o que a Q4 ainda pede.

| Endpoint | Chamado por | Para que serve |
|---|---|---|
| `GET /api/users/{userId}/permissions` | Starter, em cache miss | Permissões de um sujeito arbitrário. **Não confundir** com `GET /api/users/me/permissions`, que já existe e serve o próprio chamador: aqui quem chama é um serviço, com credenciais de serviço, a pedir as permissões de outra pessoa |
| `POST /api/routes/register` | Starter, no arranque | Registo das rotas descobertas. Upsert pela chave |
| `POST /api/authorize/page` | Biblioteca de frontend | Verificação em cascata aplicação → rota. Responde `allowed` + `reason`. Alinha com o `POST /api/authorize/check` existente |
| `POST /api/manifests/register` | Build do frontend | Registo dos manifestos de página |
| `GET /api/users/me/applications` | App Center | **Já existe** — não é um endpoint novo. Lista as aplicações do utilizador autenticado |

## 7. Permissões por rota

> **Decisão D6.** Autorização como dados, fora do código: nada de `@PreAuthorize` cravado em cada controller. As permissões passam a ser geridas em runtime, sem recompilar nem redistribuir microserviços.

### 7.1 Ciclo de vida de uma permissão de rota

1. **Descoberta.** No arranque (`ApplicationReadyEvent`), o microserviço lê as suas rotas no `RequestMappingHandlerMapping`.
2. **Registo.** Envia a lista ao serviço central, que cria uma permissão por cada rota nova e ignora as existentes.
3. **Atribuição.** No painel, o gestor atribui as permissões a roles ou diretamente a utilizadores.
4. **Verificação.** Em cada pedido, a chave da rota é derivada e comparada com as permissões no Redis.

### 7.2 Registo dinâmico

```java
@Component
class RouteRegistrar {
  @EventListener(ApplicationReadyEvent.class)
  void register() {
    var routes = handlerMapping
      .getHandlerMethods()
      .entrySet().stream()
      .flatMap(e -> RouteDto.of(e.getKey(), e.getValue(), keyResolver))
      .toList();
    central.registerRoutes(service, routes);
  }
}
```

Contrato com o serviço central (ilustrativo):

```http
POST /api/routes/register
Content-Type: application/json

{
  "service": "faturacao-api",
  "routes": [
    { "method": "GET",  "path": "/faturas/{id}",
      "key": "faturas.read",    "annotated": false },
    { "method": "POST", "path": "/faturas/{id}/aprovar",
      "key": "faturas.approve", "annotated": true }
  ]
}
```

Semântica no central: **upsert pela chave**. Rotas novas tornam-se permissões ainda sem atribuição. As existentes mantêm nome e atribuições.

### 7.3 Chave estável, nome editável

| Elemento | Papel | Regras |
|---|---|---|
| Chave | Identidade | Legível, gerada quando a rota nasce, nunca muda. É o que o código verifica. |
| Nome | Apresentação | Editável pelo gestor, em qualquer língua: "Ver faturas", "Consultar faturação". |

O gestor vê sempre os nomes, nunca as chaves técnicas.

### 7.4 Convenção `recurso.acção`

| Rota | Chave |
|---|---|
| `GET /faturas` | `faturas.list` |
| `GET /faturas/{id}` | `faturas.read` |
| `POST /faturas` | `faturas.create` |
| `PUT` ou `PATCH /faturas/{id}` | `faturas.update` |
| `DELETE /faturas/{id}` | `faturas.delete` |
| `GET /api/v1/faturas/{id}/linhas` | `faturas.linhas.list` |

Regras:

- Variáveis `{…}`, o prefixo `api` e versões (`v1`, `v2`, …) são descartados.
- `GET` com o path a terminar em variável dá `read`; a terminar em recurso dá `list`. **Decidido separar `list` de `read`.**
- `POST` → `create`; `PUT`/`PATCH` → `update`; `DELETE` → `delete`; outros métodos → nome do método em minúsculas.
- Recursos aninhados mantêm a hierarquia na chave, o que a torna legível para o gestor.
- **Língua.** O **recurso** vem do path, logo é do developer: pode estar em qualquer língua
  (`faturas`, `invoices`, `factures`) e não há obrigação nenhuma. A **acção** é gerada pela
  plataforma e é **sempre em inglês** — `read`, `list`, `create`, `update`, `delete`, ou o nome
  do método HTTP em minúsculas. A convenção automática nunca produz uma acção noutra língua,
  porque escolhe de um conjunto fechado.
- **A anotação é a excepção a vigiar.** `@Permission` é o único ponto onde um developer escreve
  uma acção à mão: em `@Permission("faturas.approve")` é ele que decide o último segmento. A
  regra acima aplica-se aí — `faturas.aprovar` seria inválido. Fica em aberto se o starter deve
  **validar** o último segmento no arranque contra o conjunto de acções permitidas, ou se basta
  a convenção de equipa (Q14).

```java
String key(String method, String path) {
  var segs = Arrays.stream(path.split("/"))
    .filter(s -> !s.isBlank() && !s.equals("api"))
    .filter(s -> !s.matches("v\\d+")).toList();
  var resources = segs.stream()
    .filter(s -> !s.startsWith("{")).toList();
  boolean endsInVariable = segs.getLast().startsWith("{");
  String action = switch (method) {
    case "GET"          -> endsInVariable ? "read" : "list";
    case "POST"         -> "create";
    case "PUT", "PATCH" -> "update";
    case "DELETE"       -> "delete";
    default             -> method.toLowerCase();
  };
  return String.join(".", resources) + "." + action;
}
```

Exemplo: `GET /api/v1/faturas/{id}/linhas` → segmentos `faturas · {id} · linhas` → recursos `faturas.linhas` + acção `list` → `faturas.linhas.list`.

A mesma função corre no arranque (para registar) e em cada pedido (para verificar). Por isso vive no starter: as duas pontas têm de usar exatamente a mesma convenção.

### 7.5 Convenção e anotação `@Permission`

| Proposta | Avaliação | Estado |
|---|---|---|
| A · Só convenção pelo path | Zero esforço, mas a chave fica refém do path | Rejeitada |
| B · Anotação obrigatória | `@Permission("faturas.read")` como âncora de identidade. Estável, mas exige disciplina total | Rejeitada |
| Convenção + anotação opcional | A convenção cobre a maioria. Quem quer travar a chave usa a anotação | **Escolhida** |

> **Decisão D7.** Convenção por omissão, `@Permission` opcional para fixar a chave.

```java
@Target(METHOD)
@Retention(RUNTIME)
public @interface Permission {
  String value();
}
```

```java
@RestController
@RequestMapping("/faturas")
class FaturaController {

  @GetMapping("/{id}")                 // convenção → faturas.read
  FaturaDto ler(@PathVariable UUID id) { … }

  @Permission("faturas.approve")
  @PostMapping("/{id}/aprovar")
  void aprovar(@PathVariable UUID id) { … }
  // sem anotação seria faturas.aprovar.create
}
```

- Ações que não são CRUD (`approve`, `cancel`, `resend`) são as melhores candidatas à anotação: a convenção pelo método HTTP dá-lhes um nome pouco intuitivo.
- Rotas importantes e estáveis devem ser anotadas desde o início.
- Renomear com segurança: se `/faturas` passar a `/invoices`, com `@Permission("faturas.read")` a chave e as atribuições mantêm-se.

> **Alerta A4. Chaves órfãs.** Mudar o path de uma rota não anotada deixa a chave antiga órfã, com as atribuições presas, e cria uma chave nova vazia. Regra da equipa: antes de mexer no path, anotar a rota com a chave antiga, ou reatribuir à mão. É mais disciplina de equipa do que problema técnico.

### 7.6 Filtro automático

> **Decisão D8.** Nenhum microserviço programa validação. Nem `@PreAuthorize`, nem `if`. O filtro de autorização é registado pela autoconfiguração e aplica-se a todas as rotas de todos os microserviços. O programador escreve o controller normal; a proteção já está por baixo.

Passos por pedido:

1. A autenticação valida o token.
2. O filtro deriva a chave da rota.
3. Lê as permissões do Redis.
4. Deixa passar, ou devolve 403.

Sequência:

```
Cliente            Resource Server     Filtro de rota        Redis            Controller
  │ GET /faturas/42 + Bearer │                 │                  │                  │
  │─────────────────────────▶│ JWT válido,     │                  │                  │
  │                          │ sub=joao ──────▶│ SMEMBERS …:joao ▶│                  │
  │                          │                 │◀ {faturas.read,…}│                  │
  │                          │                 │ faturas.read presente ─────────────▶│
  │                          │                 │ senão: 403 + auditoria "negado"     │
```

```java
class RouteAuthorizationFilter extends OncePerRequestFilter {
  protected void doFilterInternal(HttpServletRequest req,
      HttpServletResponse res, FilterChain chain) … {
    var route = routes.resolve(req);
    if (route.isPublic()) { chain.doFilter(req, res); return; }
    var user = SecurityContextHolder.getContext()
        .getAuthentication().getName();
    if (!cache.permissions(user).contains(route.key())) {
      audit.denied(user, route.key());
      res.sendError(403);
      return;
    }
    chain.doFilter(req, res);
  }
}
```

- `routes.resolve` usa o `HandlerMapping` para saber que método vai responder e aplica o `PermissionKeyResolver` (ou o valor de `@Permission`).
- `cache.permissions` é o mesmo serviço do converter: Redis primeiro, central só em miss.
- `audit.denied`: as negações também são prova de compliance.
- O filtro fica depois do `BearerTokenAuthenticationFilter` na `SecurityFilterChain`, por isso já encontra o utilizador autenticado.

### 7.7 Rotas públicas

| Via | Natureza | Exemplos |
|---|---|---|
| Anotação `@Public` no método | Público por natureza. Fica documentado ao lado da rota | Registo de conta, callback de pagamento, consulta pública |
| Lista `igrp.security.public-paths` no `application.yml` | Público por infraestrutura. Ajusta-se por ambiente sem recompilar | Health check, actuator, Swagger, estáticos |

> **Decisão D9.** As duas vias. Uma rota só é pública se for marcada explicitamente por uma delas. Tudo o resto exige permissão.

```java
@Public
@PostMapping("/registo")
ContaDto registar(…) { … }

@Public
@PostMapping("/callback/pag")
void callback(…) { … }
```

```yaml
igrp:
  security:
    public-paths:
      - /actuator/health
      - /v3/api-docs/**
      - /swagger-ui/**
      - /static/**
```

```java
boolean isPublic(Route r) {
  return r.hasPublicAnnotation()
      || props.publicPaths().stream()
           .anyMatch(p -> matcher.match(p, r.path()));
}
// resto: exige permissão
```

> **Alerta A5. Falhar do lado seguro.** Nunca o contrário. Uma rota sem marcação fica protegida. Bloquear por engano vê-se nos testes; expor por engano é um incidente de segurança. Os testes devem cobrir rotas sem permissão.

## 8. Autorização fina de dados

Há dois níveis de autorização:

| Nível | Pergunta | Onde se resolve |
|---|---|---|
| 1 · Rota | "Pode chamar `GET /faturas`?" | Starter: permissões por rota e Redis |
| 2 · Dado | Dentro da rota, que **linhas** vê (por exemplo, só as dele por ser dono) e que **colunas** (nível insuficiente esconde campos) | No serviço, com âmbitos e filtragem de campos |

### 8.1 Zanzibar e alternativas

| Proposta | Avaliação | Estado |
|---|---|---|
| Google Zanzibar / ReBAC (OpenFGA, SpiceDB) | Só compensa com relações complexas (herança, grupos, partilhas). Trazer um sistema de relações distribuído para resolver um `WHERE` seria infraestrutura a manter e sincronizar sem ganho real | **Rejeitada** |
| Filtro na query | "Só vê os dele" = `WHERE owner_id = ?` | **Adotada** |
| Field-level na resposta | Esconder colunas filtrando campos conforme as permissões | **Adotada** |

> **Decisão D10.** Sem Zanzibar. Três portas: rota (starter), linhas (filtro na query), colunas (filtragem de campos).

```
Pedido GET /faturas
  → Porta 1 · rota     faturas.list? senão 403
  → Porta 2 · linhas   WHERE owner_id = :user
  → Porta 3 · colunas  remove campos sem nível
```

Exemplo com dados fictícios. O gestor financeiro recebe:

```json
[ { "id": 123, "cliente": "Atlântico, Lda", "valor": 500.00, "margem": 0.18 },
  "… todas as faturas …" ]
```

O técnico recebe:

```json
[ { "id": 123, "cliente": "Atlântico, Lda", "valor": 500.00 },
  "… só as faturas de que é dono …" ]
```

A coluna `margem` só segue para quem tem a permissão correspondente, por exemplo `faturas.margem.read`. O mecanismo concreto de filtragem de campos não foi detalhado no debate (Q5).

### 8.2 Âmbitos de visibilidade

Caso de referência: lista de tarefas da gestão de processos. O administrador vê todas; o utilizador vê as suas ou as atribuídas a um dos seus roles. Os roles são dinâmicos e cada utilizador tem vários.

| Âmbito | Exemplo de role | Condição gerada |
|---|---|---|
| `all` | Administrador · `tarefas.list` | sem filtro |
| `own` | Técnico · `tarefas.list` | `owner_id = :user` |
| `by_role` | Supervisor · `tarefas.list` | `assigned_role IN (:roles)` |

> **Decisão D11. Onde vive o âmbito.** É atribuído com a permissão ao role, no serviço central. Dados, não código. Um role criado amanhã recebe o seu âmbito no painel, sem recompilar nada.
>
> **Decisão D12. Vários roles.** União dos âmbitos: o mais permissivo ganha. Condições ligadas por `OR`. Nunca interseção.

Tabela `role_permission` (ilustrativa):

| role | permission | scope |
|---|---|---|
| Administrador | tarefas.list | all |
| Técnico | tarefas.list | own |
| Supervisor | tarefas.list | by_role |

Exemplos:

- **Maria (Técnico + Supervisor)**: `own ∪ by_role`
  ```sql
  WHERE owner_id = :maria
     OR assigned_role IN ('TECNICO', 'SUPERVISOR')
  ```
- **Ana (Técnico + Administrador)**: `own ∪ all` → `all` ganha. Sem filtro: vê todas as tarefas.

### 8.3 Como aplicar o âmbito em todas as queries

| Proposta | Avaliação | Estado |
|---|---|---|
| Mini-linguagem de regras | Motor próprio de regras e SQL, sem casos concretos | Adiada |
| Âmbitos como estratégias | Cada âmbito traduz-se num pedaço de `WHERE` | **Adotada** |
| `@PostFilter` (Spring) | Filtra em memória: parte a paginação | Rejeitada |
| Hibernate `@Filter` | Injeta a condição em todas as queries da entidade | **Adotada** |
| Row-Level Security (PostgreSQL) | Decisão na própria base | Alternativa, não adotada |

> **Decisão D13.** A lógica de âmbitos decide qual é a condição; o Hibernate `@Filter` aplica-a sem que ninguém se esqueça de uma query. Nada no Spring resolve isto de ponta a ponta.

Entidade (ilustrativa):

```java
@Entity
@FilterDef(name = "scope", parameters = {
  @ParamDef(name = "user", type = UUID.class),
  @ParamDef(name = "own",     type = Integer.class),
  @ParamDef(name = "byRole",  type = Integer.class),
  @ParamDef(name = "roles",      type = String.class) })
@Filter(name = "scope", condition =
  "(:own = 1 and owner_id = :user)" +
  " or (:byRole = 1 and assigned_role in (:roles))")
class Tarefa { … }
```

Ativação por pedido (starter):

```java
var a = scopes.resolve(user, "tarefas.list");
if (!a.all()) {
  session.enableFilter("scope")
    .setParameter("user", user.id())
    .setParameter("own", a.own())
    .setParameter("byRole", a.byRole())
    .setParameterList("roles", user.roles());
}
```

- Âmbito `all`: o filtro nem é ativado.
- Acrescentar um âmbito novo = uma nova estratégia que liga a sua flag + um novo ramo `OR` na condição.

> **Alerta A6. Filtros ativos somam-se com AND.** Um filtro Hibernate por âmbito daria interseção, não união. A união tem de estar numa só condição com `OR`; cada estratégia liga a sua flag.
>
> **Alerta A7. Mini-linguagem cedo de mais.** Reabrir só com três casos reais que não caibam nas estratégias. Antes disso é um motor de segurança sem requisitos.

## 9. Frontends

### 9.1 Esconder e bloquear

| Mecanismo | Tipo | Comportamento |
|---|---|---|
| App Center | Experiência | Lista só as aplicações a que o utilizador tem acesso, a partir de um endpoint do central (`GET /api/users/me/applications`) |
| Deep link | Bloqueio duro | Um link colado no browser por quem não tem acesso é barrado antes de renderizar |

> **Decisão D14.**
> - A rota de frontend tem **permissão própria**, independente das APIs que a página consome.
> - Uma só pergunta, ao serviço central. O browser nunca decide.
> - Biblioteca fina por framework: Next.js hoje, Angular depois. Só pergunta e aplica; a lógica de decisão vive no backend.
> - Cada API continua protegida pelo filtro do starter. A página abre e uma secção pode vir vazia.

Pergunta levantada no debate: se a página consome vários microserviços, a quem pergunta? A nenhum deles. A permissão de abrir a página vive no central; cada microserviço protege os seus dados de forma independente.

### 9.2 Deep link: fluxo

```
Browser /faturacao/detalhe/42
  → Shell · middleware (@igrp/access-next)
      sem cookie de sessão ─▶ redirect /login?returnTo=<path>  (não pergunta ao central)
      com sessão          ─▶ serviço central: app? rota? (via Redis)
                               ├─ tem app e rota ─▶ renderiza; APIs protegidas pelo starter
                               └─ negado         ─▶ rewrite para /sem-acesso; nada da página é enviado
```

Resposta do central: `allowed` + `reason`.

### 9.3 Biblioteca por framework

Next.js (`shell/middleware.ts`):

```ts
import { NextResponse, type NextRequest } from "next/server";
import { checkAccess } from "@igrp/access-next";

export async function middleware(req: NextRequest) {
  const session = req.cookies.get("igrp_session")?.value;
  if (!session) return NextResponse.redirect(
    new URL(`/login?returnTo=${req.nextUrl.pathname}`, req.url));
  const r = await checkAccess(session, req.nextUrl.pathname);
  return r.allowed
    ? NextResponse.next()
    : NextResponse.rewrite(new URL("/sem-acesso", req.url));
}
```

Angular (futuro):

```ts
export const accessGuard: CanActivateFn =
  async (_r, state) =>
    (await inject(Access).check(state.url)).allowed ||
    inject(Router).parseUrl("/sem-acesso");
```

Suportar Angular é escrever um guard fino, não reimplementar regras.

### 9.4 Manifesto por página

O gestor deixa de gerir chaves crípticas e passa a gerir páginas e capacidades, a linguagem que entende.

Manifesto da página "Detalhe de faturas":

| Campo | Exemplo |
|---|---|
| Chave da página | `app.faturacao.detalhe` |
| Obrigatórias | `faturas.read`, `clientes.read`, `pagamentos.list` |
| Opcionais | `faturas.export` |
| Aplicação lógica | Faturação |

| Proposta | Estado |
|---|---|
| Manifesto mantido à mão, ao lado da página, auto-registado no central | **Adotada** |
| Descoberta automática das APIs que a página chama | Adiada |

> **Decisão D15.** Manifesto à mão, ao lado da página. No build é enviado ao central tal como as rotas do backend. Conceder a página concede as obrigatórias de uma vez; as opcionais são escolhas do gestor.

Onde vive:

```
apps/faturacao-web/app/detalhe/[id]/
├── page.tsx
└── access.manifest.ts
```

```ts
export default defineManifest({
  application: "faturacao",
  page: "app.faturacao.detalhe",
  required: ["faturas.read", "clientes.read", "pagamentos.list"],
  optional: [{ key: "faturas.export", label: "Exportar PDF" }],
});
```

Esboço do ecrã do gestor: "Conceder *Detalhe de faturas* ao role Técnico". Incluídas automaticamente: Ver faturas, Ver clientes, Listar pagamentos. Opcionais: Exportar PDF. Botão Conceder. O gestor vê os nomes legíveis, nunca as chaves.

> **Alerta A8. O manifesto pode mentir.** Uma API nova chamada pela página e não declarada faz uma secção falhar sem explicação. Prever validação em CI: APIs chamadas contra APIs declaradas.

### 9.5 Micro-frontends e aplicação lógica

| Camada | O que é |
|---|---|
| 1 · Aplicação lógica | Registada no central, não no IDP. É o que o gestor atribui e o App Center lista |
| 2 · Micro-frontends | Shell Next.js com multi-zone. Detalhe técnico, invisível ao modelo de acesso |
| 3 · Ponte | O manifesto de cada página declara a que aplicação lógica pertence |

> **Decisão D16.** A aplicação lógica é a fronteira de acesso. Verificação em cascata: (1) pergunta grossa, tem acesso à aplicação? (2) pergunta fina, tem a permissão da rota? Só passa com sim às duas.

Exemplo de mapeamento:

| Zona técnica | Caminho | Aplicação lógica |
|---|---|---|
| `faturacao-web` | `/faturacao/*` | Faturação |
| `relatorios-web` | `/faturacao/relatorios/*` | Faturação |
| `rh-web` | `/rh/*` | Recursos Humanos |

Faturação tem duas zonas e uma só entrada no App Center. Partir ou juntar zonas não muda nenhuma atribuição de acesso.

Identidade do frontend: hoje o frontend reutiliza o token do utilizador, que é o padrão normal. Identidade própria do frontend (`client_id` com Authorization Code + PKCE) só se torna necessária para chamadas sem utilizador, para saber que app está a chamar, ou para limitar o que cada app faz.

## 10. Machine-to-machine e agentes

### 10.1 Client Credentials

Situação atual: tabela própria no central com tokens M2M, roles e escopos atribuídos. É um segundo mecanismo de identidade, à parte do IDP. Tokens fixos de longa duração não expiram sozinhos; um vazamento num log ou num dump dá acesso de máquina até à revogação manual.

> **Decisão D17.** Substituir a tabela por **OAuth2 Client Credentials**. Cada microserviço é cliente no IDP (`client_id` e `client_secret`), pede um token curto e o serviço alvo valida-o no mesmo Resource Server (starter). Os escopos de cada serviço ficam no cliente registado no IDP; o central pode associar permissões à identidade de serviço.

Fluxo:

1. `faturacao-api` verifica se tem token em cache.
2. Se não tem, pede ao IDP com `grant_type=client_credentials`.
3. Recebe um token curto com `sub = faturacao-api`.
4. Chama `clientes-api`, que valida o token no starter.

```yaml
spring.security.oauth2.client:
  registration.igrp-idp:
    client-id: faturacao-api
    client-secret: ${FATURACAO_CLIENT_SECRET}
    authorization-grant-type: client_credentials
    scope: clientes.read
  provider.igrp-idp:
    token-uri: https://idp.igrp/oauth/token
```

O `OAuth2AuthorizedClientManager` guarda e renova o token.

> **Alerta A9. Secrets.** O `client_secret` vem de um cofre (Vault, Secrets do Kubernetes), injetado como variável de ambiente. Nunca em configuração no repositório.
>
> **Alerta A10. Cache do token.** Pedir uma vez e guardar em memória até perto de expirar. Não pedir token a cada chamada.

### 10.2 Preservar o utilizador ao longo da cadeia

| Proposta | Avaliação | Estado |
|---|---|---|
| Reenviar o token do utilizador | Rasto completo, mas o token espalha-se por muitos serviços | Rejeitada |
| Só o token do serviço | Isolado, mas perde o utilizador original | Rejeitada |
| Token Exchange (OAuth2, RFC 8693) | "Serviço A em nome do utilizador X": as duas identidades | **Adotada** |

> **Decisão D18. Regra dos dois caminhos.**
> - Há utilizador na origem → **Token Exchange**. Permite decidir permissões pelo utilizador no fim da cadeia, não só auditar.
> - Processo de fundo sem utilizador (jobs, limpezas agendadas) → **Client Credentials**, em nome do próprio serviço.

O utilizador viaja na cadeia como sujeito; os serviços como atores. Em cada salto, o serviço troca o token que recebeu por um novo, dirigido ao serviço seguinte. A claim `act` regista a cadeia de atores; `sub` continua a ser o João, por isso o serviço C pode decidir pelas permissões dele.

```jsonc
// token 1 · A (faturacao-api) recebe
{ "sub": "joao", "aud": "faturacao-api" }

// token 2 · B (clientes-api) recebe
{ "sub": "joao", "aud": "clientes-api",
  "act": { "sub": "faturacao-api" } }

// token 3 · C (moradas-api) recebe
{ "sub": "joao",
  "act": { "sub": "clientes-api",
    "act": { "sub": "faturacao-api" } } }
```

Pedido do serviço A ao IDP, autenticado com as credenciais de `faturacao-api`:

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<token do João recebido pelo serviço A>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=clientes-api
&scope=clientes.read
```

O starter deve encapsular este pedido, para que a troca de fornecedor de IDP não afete os serviços.

> **Alerta A11. Sobrecarga do IDP.** Trocar só ao cruzar fronteiras e reutilizar o token trocado.
>
> **Alerta A12. Confirmar no IDP.** O suporte e a configuração de token exchange variam entre fornecedores e versões. Validar que o IDP configurado (Keycloak, Auth0) o suporta, e com que restrições, antes de implementar (Q7).

### 10.3 Agentes de IA

| Tipo de agente | Mecanismo | Regra |
|---|---|---|
| Em nome de alguém | Token Exchange | `sub` = utilizador, `act` = agente. Pode no máximo o que o utilizador pode, recortado pelo escopo do agente |
| Autónomo | Client Credentials | Cliente próprio no IDP com escopo mínimo, revisto como qualquer conta de serviço |

> **Decisão D19.** Sem quarta categoria. Cada agente novo é classificado com uma pergunta: age em nome de um utilizador? Sim → Token Exchange. Não → Client Credentials.

> **Alerta A13. Agentes.** Um agente pode decidir chamadas que ninguém anteviu. Em ambos os casos: escopo mínimo, auditoria com o agente identificado como ator, alertas sobre volumes anómalos de chamadas. São o caso mais sensível para deteção de anomalias.

## 11. Auditoria e observabilidade

Motivação: logs perdidos no stream do Auth0. Necessidades: compliance (procurement, contratos públicos) e segurança operacional.

### 11.1 Três registos, um fio

| Registo | Pergunta | Natureza | Retenção |
|---|---|---|---|
| Auditoria | Quem fez o quê, quando | Registo de negócio. Imutável, permanente, para compliance e investigação | Anos |
| Logs | O que correu e o que falhou | Registo técnico, verboso, para depurar | Curta |
| Tracing | Por onde passou o pedido | Identificador de correlação que viaja por toda a cadeia | Curta |

O identificador de correlação (W3C Trace Context) entra também nos registos de auditoria. De "o João aprovou a fatura 123" salta-se para o rasto técnico completo.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

| Destino | Tecnologia (referida no debate) | Conteúdo |
|---|---|---|
| Auditoria | Base própria, append-only | `trace_id` em cada evento |
| Logs | Loki ou Elasticsearch | Pesquisa por traceId |
| Traces | Tempo | A jornada do pedido, salto a salto |

Logs e traces seguem para uma stack de observabilidade (Elasticsearch, ou Grafana com Loki e Tempo) com retenção curta e alertas. A escolha está em aberto (Q9).

### 11.2 Quem regista

| Proposta | Avaliação | Estado |
|---|---|---|
| Tudo no Access Management | Ele nem vê a maioria das ações, porque os serviços leem do Redis. Voltaria a ser o gargalo que o Redis eliminou | **Rejeitada** |
| Quem pratica a ação regista-a | Cada um audita o que conhece | **Adotada** |

> **Decisão D20.**
> - **Access Management** regista decisões de acesso: entradas em aplicações, emissão de tokens, permissões concedidas ou negadas.
> - **Cada microserviço** regista ações de negócio ("aprovou a fatura 123"). Só o serviço conhece o detalhe. A mecânica vem do starter: formato fixo, identificador de correlação incluído, identidade extraída do token. O serviço só diz "regista esta ação".

```java
@Transactional
public void aprovar(UUID id) {
  var f = faturas.getReferenceById(id);
  f.aprovar();
  audit.record(
    "fatura.approved",
    Resource.of("fatura", id),
    Map.of("valor", f.getValor()));
}
// quem, quando, traceId e agente: preenchidos pelo starter
```

Evento gravado:

```json
{
  "event": "fatura.approved",
  "who": { "user": "joao", "via": "faturacao-api", "agent": null },
  "resource": { "type": "fatura", "id": "123" },
  "result": "success",
  "occurredAt": "2026-10-14T09:12:03Z",
  "traceId": "4bf92f35…0e4736"
}
```

Cada evento de compliance guarda sempre: **quem** (utilizador, e se foi via agente ou serviço), **o quê**, **sobre o quê**, **quando** e o **resultado**, incluindo negações.

### 11.3 Colunas, Envers e log de eventos

| Necessidade | `created_by` / `updated_by` | Hibernate Envers | Log de eventos |
|---|---|---|---|
| Estado atual e último autor | Sim | Sim | Não |
| História completa | Não | Sim | Sim |
| Antes e depois | Não | Sim | Não |
| Leituras sensíveis | Não | Não | Sim |
| Acessos negados | Não | Não | Sim |
| Tokens, exportações, agentes | Não | Não | Sim |

> **Decisão D21.** Manter os três. O log de eventos fica magro: só o que o Envers não apanha. Envers e log de eventos ligam-se pelo identificador de correlação. A mecânica do starter pode preencher as colunas da linha e emitir o evento no mesmo gesto.

```java
@Entity @Audited
class Fatura {
  @Id UUID id;
  BigDecimal valor;
  String estado;
  @CreatedBy String createdBy;
  @LastModifiedBy String updatedBy;
}

@RevisionEntity(IgrpRevListener.class)
class IgrpRevision {
  String username;
  String traceId;
}
```

O listener de revisão grava `username` e `traceId`. Exemplo com dados fictícios:

`fatura_aud`

| rev | tipo | valor | estado |
|---|---|---|---|
| 101 | ADD | 100.00 | RASCUNHO |
| 102 | MOD | 500.00 | RASCUNHO |
| 103 | MOD | 500.00 | APROVADA |

`revinfo` (revisão personalizada)

| rev | username | occurred_at | trace_id |
|---|---|---|---|
| 101 | ana | 09:02 | a71c… |
| 102 | ana | 09:07 | c09e… |
| 103 | joao | 09:12 | 4bf9… |

### 11.4 Onde aterram os eventos

| Proposta | Avaliação | Estado |
|---|---|---|
| Cada serviço, a sua base | Desacoplado, mas investigar exige cruzar várias bases | Rejeitada |
| Base central partilhada | Pesquisa fácil, mas ponto único de falha | Rejeitada |
| Local + broker + central | Garantido na origem, pesquisável no central | **Adotada** |

> **Decisão D22.** Origem garantida, consolidação assíncrona, com transactional outbox.

```
Serviço · uma transação
  BEGIN;
  UPDATE fatura …;
  INSERT INTO audit_event …;
  INSERT INTO audit_outbox …;
  COMMIT;
        │
        ▼
  Relay (lê o outbox) ──assíncrono──▶ Kafka · igrp.auditoria (ou RabbitMQ) ──▶ Armazém central
                                                                                consolidado e pesquisável:
                                                                                tudo o que uma pessoa fez,
                                                                                em todos os serviços
```

Se o broker falhar, `audit_event` já existe na origem e o outbox volta a publicar quando o broker regressar.

Tabelas (ilustrativas):

```sql
CREATE TABLE audit_event (
  id           UUID PRIMARY KEY,
  event        VARCHAR(100) NOT NULL,
  username     VARCHAR(100),
  agent        VARCHAR(100),
  resource     VARCHAR(150),
  result       VARCHAR(20)  NOT NULL,
  trace_id     VARCHAR(32),
  occurred_at  TIMESTAMPTZ  NOT NULL,
  payload      JSONB
);
REVOKE UPDATE, DELETE ON audit_event FROM igrp_app;

CREATE TABLE audit_outbox (
  id            UUID PRIMARY KEY,
  event_id      UUID NOT NULL,
  payload       JSONB NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL,
  published_at  TIMESTAMPTZ
);
-- o relay publica as linhas com published_at IS NULL
-- e marca-as depois do ack
```

O utilizador da aplicação (`igrp_app`, nome ilustrativo) só pode inserir em `audit_event`. O outbox é a única tabela que muda, e só no campo de publicação. Append-only garantido pela base, não pela boa vontade.

> **Alerta A14. Lição do Auth0.** A prova de compliance nunca depende de um sistema externo nem de um pipeline que possa falhar. Escrita síncrona na transação; nada dependente do stream do IDP. Append-only: sem `UPDATE` nem `DELETE`.

## 12. Notas de implementação (fora do debate)

Estes pontos **não foram discutidos no debate**. Saíram da leitura do código ilustrativo e devem ser confirmados pela equipa antes ou durante a implementação.

| # | Onde | Observação | Sugestão |
|---|---|---|---|
| N1 | `PermissionCacheService` | Um utilizador sem nenhuma permissão devolve um set vazio. Como o código trata vazio como miss, esse utilizador chama o central em todos os pedidos. | Guardar um marcador de "set vazio" (ou uma chave irmã) para que o vazio também fique em cache. |
| N2 | `PermissionCacheService` | Corrida entre miss e invalidação: o pedido A lê o central (dados antigos), o central faz commit e `DEL`, e só depois A grava os dados antigos no Redis. Ficam válidos até ao TTL. | Aceitar como risco limitado pelo TTL (que é a rede de segurança decidida em D3), ou versionar a chave. |
| N3 | `PermissionCacheService` | `SADD` e `EXPIRE` são dois comandos. Se o processo cair entre os dois, a chave fica sem TTL. | Usar pipeline/transação (`MULTI`) ou script Lua. |
| N4 | `RouteAuthorizationFilter` | Num pedido sem token, `getAuthentication()` é anónimo e `getName()` devolve `anonymousUser`; o filtro iria procurar permissões para esse nome. | Devolver 401 antes da consulta quando não há autenticação. |
| N5 | `SecurityFilterChain` | O Spring Security tem a sua própria regra final (`authorizeHttpRequests`). Se ficar `anyRequest().authenticated()`, as rotas públicas da secção 7.7 são barradas com 401 antes de contarem como públicas. | Alinhar a regra do Spring com `@Public` e `public-paths` (por exemplo, `permitAll` nas públicas e `authenticated` no resto, com o filtro a decidir o 403). |
| N6 | `PermissionKeyResolver` | O código descarta `api` e `vN` em qualquer posição do path, não só no prefixo. Um recurso chamado `api` no meio do path desaparece da chave. Com path `/` a lista de segmentos fica vazia e `getLast()` rebenta. | Decidir se a regra é só de prefixo e tratar o path raiz. Cobrir com testes de tabela. |
| N7 | `RouteAuthorizationFilter` | Uma rota sem handler (404) não tem chave. | Definir se passa para o 404 normal ou se responde 403. |
| N8 | Hibernate `@Filter` | Os filtros aplicam-se a queries (HQL, Criteria, coleções), não a carregamentos diretos por id (`find`, `getReferenceById`). Um `GET /tarefas/{id}` pode ler uma linha fora do âmbito. | Validar o âmbito também nas leituras por id, ou carregar por query. |
| N9 | Hibernate `@Filter` | Com `roles` vazio, `in (:roles)` pode gerar SQL inválido em alguns dialetos. | Passar sempre pelo menos um valor neutro, ou desligar o ramo quando não há roles. |
| N10 | Hibernate `@Filter` | O filtro tem de estar ativo na mesma `Session` que faz a query. Em Spring, isso implica ativá-lo no início da transação/pedido. | Ativar num interceptor do starter, ligado ao pedido. |

## 14. Registo de decisões

| ID | Tema | Decisão |
|---|---|---|
| D1 | Modelo de permissões | Token magro; permissões carregadas por pedido (modelo 2) |
| D2 | Cache | Redis partilhado, `permissions:user:{id}`, cache-aside |
| D3 | TTL | 30 a 60 minutos, como rede de segurança |
| D4 | Invalidação | O central apaga a chave do utilizador depois do commit |
| D5 | Distribuição | `igrp-security-starter` com autoconfiguração; zero código de segurança nos serviços |
| D6 | Autorização por rota | Como dados, sem `@PreAuthorize`; registo dinâmico no arranque |
| D7 | Chave | `recurso.acção`, `list` separado de `read`, `@Permission` opcional. Recurso em qualquer língua (é do developer); **acção sempre em inglês** (é gerada pela plataforma) |
| D8 | Validação | Filtro automático no starter |
| D9 | Rotas públicas | `@Public` ou `public-paths`; fechado por omissão |
| D10 | Autorização de dados | Sem Zanzibar; rota, linhas, colunas |
| D11 | Âmbitos | Atribuídos com a permissão ao role, no central |
| D12 | Vários roles | União dos âmbitos com `OR` |
| D13 | Aplicação do âmbito | Estratégias + Hibernate `@Filter` |
| D14 | Frontends | Permissão própria da rota de frontend; o central decide; biblioteca fina por framework |
| D15 | Manifesto | À mão, ao lado da página, auto-registado no central |
| D16 | Micro-frontends | Aplicação lógica como fronteira; verificação em cascata app → rota |
| D17 | M2M | Client Credentials substitui a tabela de tokens |
| D18 | Cadeias de serviços | Token Exchange com utilizador na origem; Client Credentials sem utilizador |
| D19 | Agentes | Sem quarta categoria; em nome de utilizador ou autónomo |
| D20 | Quem audita | Access Management audita acesso; cada serviço audita negócio, com a mecânica do starter |
| D21 | Ferramentas de auditoria | Colunas + Envers + log de eventos magro |
| D22 | Destino da auditoria | Outbox na origem, broker, armazém central |

## 15. Registo de alertas e riscos

| ID | Risco | Mitigação |
|---|---|---|
| A1 | Invalidação antes do commit reintroduz permissões antigas | Invalidar em `AFTER_COMMIT` |
| A2 | TTL curto sem invalidação sobrecarrega o central | TTL longo + invalidação ativa |
| A3 | Starter não carregado | Ficheiro `AutoConfiguration.imports` presente e testado |
| A4 | Chaves órfãs | Antes de mudar o path de rota não anotada, anotar com a chave antiga, ou reatribuir |
| A5 | Rota exposta | Público só por marcação explícita; testes cobrem rotas sem permissão |
| A6 | Filtros Hibernate somam-se com AND | Uma só condição com `OR` e flags por âmbito |
| A7 | Mini-linguagem cedo de mais | Reabrir só com três casos reais que não caibam nas estratégias |
| A8 | Manifesto desatualizado | Validação em CI entre APIs chamadas e declaradas |
| A9 | Secrets M2M | Cofre (Vault, Secrets do Kubernetes); nunca no repositório |
| A10 | Pedir token a cada chamada | Cache do token até perto de expirar |
| A11 | Sobrecarga do IDP | Token Exchange só ao cruzar fronteiras; reutilizar o token trocado |
| A12 | IDP sem suporte de token exchange | Confirmar antes de implementar; encapsular no starter |
| A13 | Agentes | Escopo mínimo, auditoria forte, alertas sobre volumes anómalos |
| A14 | Perda de auditoria | Escrita síncrona na transação (outbox); nada dependente do stream do IDP |

## 16. Glossário

| Termo | Significado |
|---|---|
| Serviço central | Serviço Spring Boot de autorização: roles, permissões, aplicações lógicas |
| IDP | Fornecedor de identidade federado (Keycloak, Auth0 ou outro) |
| Starter | `igrp-security-starter`, dependência Spring Boot com toda a segurança dos microserviços |
| Chave de permissão | Identificador estável `recurso.acção` verificado pelo código |
| Nome de permissão | Rótulo editável que o gestor vê |
| Âmbito | Visibilidade de linhas associada a uma permissão num role: `all`, `own`, `by_role` |
| Aplicação lógica | Unidade de acesso registada no central, listada no App Center; pode ser servida por várias zonas |
| Zona | Micro-frontend técnico servido pelo shell Next.js multi-zone |
| Manifesto | Ficheiro ao lado de uma página que declara a chave da página, permissões obrigatórias e opcionais e a aplicação lógica |
| Client Credentials | Fluxo OAuth2 em que um serviço obtém token em nome próprio |
| Token Exchange | Fluxo OAuth2 (RFC 8693) em que um serviço troca o token do utilizador por outro dirigido ao serviço seguinte, mantendo `sub` e registando atores em `act` |
| Outbox | Tabela escrita na mesma transação que a ação, depois publicada no broker por um relay |
