# Internationalization (i18n)

How the Access Management API translates the text it returns — error messages, Bean
Validation messages and exported report labels — and how to add or change a translation.

Source of truth for the design decisions: `access-management/_specs/i18n/requirements.md`
and `plan.md`. This page documents what the code actually does.

---

## 1. The model

### Platform languages

The platform language list is fixed in code and is **not** configurable:

| Language | Tag | Formatting region |
|---|---|---|
| Portuguese | `pt` | `pt-CV` |
| English | `en` | `en-GB` |
| French | `fr` | `fr-FR` |

It lives in `shared/i18n/IgrpLocale.java`. Only the **base tag** (`pt`, `en`, `fr`) is
ever stored or sent over the wire; the region is used solely for date/number formatting.

### Module default vs. platform default

Two different defaults, easy to confuse:

- **Module default** (`igrp.i18n.default-locale`, `en`) — the language of the base
  bundle `messages.properties`. This bundle **must be complete**: it is the second step
  of the message fallback chain.
- **Platform default** (`igrp.i18n.platform-default-locale`, `pt`) — used **only** to
  pick the *requested* locale when the request carries no supported `Accept-Language`.
  It **never** participates in message fallback.

### Message fallback (per key)

```
messages_<requested>.properties  →  messages.properties (module default, en)  →  the key itself + one WARN
```

The chain is per **key**, not per file: a partial `messages_pt.properties` is by design.
Any key missing from it falls back to the English text from the base bundle, so a screen
can legitimately mix languages while a translation is incomplete.

There is deliberately no `messages_en.properties`: with
`spring.messages.fallback-to-system-locale=false`, `en` resolves straight to the base
file. `MessageBundleConsistencyTest` fails the build if such a file is added.

The last step is implemented by `shared/i18n/Messages.java`, which returns the key (or a
caller-supplied default) and logs `Missing i18n message key '<key>' …` once per key.

## 2. Locale resolution

`shared/i18n/IgrpLocaleResolver.java` is registered as Spring's `localeResolver` bean:

1. Read the `Accept-Language` header.
2. Parse it into language ranges ordered by descending q-value (`q=0` entries dropped).
3. Return the first range that normalizes to a platform language.
4. If nothing matches — no header, malformed header, only unsupported languages — return
   the **platform default**.

Normalization (`IgrpLocale.fromTag`) collapses regional, underscore and upper-case
spellings to the base language: `pt-CV`, `pt_PT`, `pt-BR`, `PT` → `pt`.

The resolved locale is always a base language, never a region, so the server OS / JVM
locale can never leak into a response. `setLocale(...)` throws: the API is stateless and
the locale cannot be changed per request.

The Application Center resolves the user's language on its side (preference → cookie →
`Accept-Language`) and sends the **already resolved** locale in `Accept-Language` on
every API call. The API itself does no DB lookup to resolve the locale.

## 3. Configuration reference

In `src/main/resources/application.properties`:

| Property | Value | Why |
|---|---|---|
| `spring.messages.basename` | `i18n/messages` | Bundle location. |
| `spring.messages.encoding` | `UTF-8` | Bundles are UTF-8, not ISO-8859-1. |
| `spring.messages.fallback-to-system-locale` | `false` | Without this, an unresolved key falls back to the *server OS* locale bundle. The language must depend only on the request. |
| `spring.messages.always-use-message-format` | `true` | Error texts are `MessageFormat` patterns; this renders them identically whether or not arguments are supplied. **Consequence:** a literal single quote must be written `''` in *every* value, including argument-less ones. |
| `spring.messages.use-code-as-default-message` | `false` | If `true`, the validator stops resolving Hibernate's own default constraint messages. Missing keys are handled by `Messages` instead (key + WARN). |
| `igrp.i18n.default-locale` | `en` | Module default. Tied to the contents of `messages.properties`, so it is intentionally **not** environment-overridable. |
| `igrp.i18n.platform-default-locale` | `pt` (env `IGRP_I18N_PLATFORM_DEFAULT_LOCALE`) | Platform default. |

Both `igrp.i18n.*` values are validated at startup against `IgrpLocale`
(`I18nProperties.afterPropertiesSet`). **A value outside `pt`/`en`/`fr` fails application
startup** with `Invalid igrp.i18n.default-locale='xx': must be one of the platform
languages [pt, en, fr]`.

At startup `I18nConfig` also binds the platform default as the `LocaleContextHolder`
default and logs a WARN for any `i18n/messages_<lang>.properties` whose language is not a
platform language (such a bundle is simply never selected).

## 4. Bundles and message keys

Files live in `src/main/resources/i18n/`:

```
messages.properties      # en — module default, must be complete
messages_pt.properties   # partial
messages_fr.properties   # partial
```

Rules: Spring's underscore suffix (`messages_pt`, not `messages-pt`), UTF-8,
`java.text.MessageFormat` values, positional placeholders only (`{0}`, `{1}` — never
named ones like `{max}`), and `''` for a literal single quote.

Key groups:

| Group | Pattern | Example |
|---|---|---|
| API errors | `error.<IGRP_ERROR_CODE>` | `error.IGRP_AUTH_USER_NOT_FOUND_BY_ID=User not found with id: {0}` |
| Handler titles | `error.handler.<name>` | `error.handler.validationErrors=Validation Errors` |
| Bean Validation | `validation.<field>.<rule>` | `validation.email.required=The field <email> is required` |
| Reports | `report.*` | `report.audit.column.username=Username` |

### Translating a message

1. Find the key in `messages.properties`.
2. Add the same key to `messages_pt.properties` and/or `messages_fr.properties` with the
   translated value, keeping **exactly** the same `{n}` placeholders.
3. Escape literal single quotes as `''` (`l''utilisateur`, `n''existe pas`).
4. Run the consistency test.

### The consistency test

`src/test/java/.../shared/i18n/MessageBundleConsistencyTest.java` runs with the ordinary
test suite (no CI change) and enforces:

- every `IgrpErrorCode` value has an `error.<CODE>` entry in `messages.properties`, with
  the **same text** as the enum's English template;
- every key used by code — `{validation.*}` annotations, `messages.get("…")` /
  `messages.getOrDefault("…")` call sites, `report.*` from `ReportColumns` — exists in
  the base bundle;
- `messages_pt` / `messages_fr` contain no key that is absent from the base bundle;
- shared keys carry identical `{n}` placeholder sets;
- every file is valid UTF-8 and every value is a valid `MessageFormat` pattern with no
  stray single quote;
- no `messages_en.properties` exists.

It also prints per-locale coverage (informational only — partial bundles are allowed).

Run it (JDK 26 needs JaCoCo disabled — see `CLAUDE.md` for the general build commands):

```bash
mvn test -Dtest=MessageBundleConsistencyTest "-Djacoco.skip=true"
```

## 5. How to…

### Add a new error code

1. Add the constant to `shared/domain/exceptions/IgrpErrorCode.java` with its HTTP status
   and an English `MessageFormat` template.
2. Add `error.<NEW_CODE>=<the same English text>` to `messages.properties`. The
   consistency test compares the two character by character.
3. Optionally translate it in `messages_pt` / `messages_fr`.
4. Throw it as usual: `IgrpResponseStatusException.of(IgrpErrorCode.NEW_CODE, arg0, …)`.

`GlobalExceptionHandler` builds a **copy** of the exception's `ProblemDetail` whose
`title` and `detail` hold `messages.getOrDefault(code.messageKey(), code.formatMessage(args), args)`
— i.e. the bundle text in the request locale, or the enum's English template as a last
resort. The `code` property and every other property are untouched, so the response shape
is unchanged for existing clients. Exceptions built with the free-text factories (no
`IgrpErrorCode`) are returned as-is.

### Translate the validation of a new DTO

Bean Validation is wired to the application `MessageSource` by `I18nConfig.validator(...)`
(`LocalValidatorFactoryBean.setValidationMessageSource`), so a message written as a key in
braces is resolved from the same bundles:

```java
@NotBlank(message = "{validation.email.required}")
@Email(message = "{validation.email.invalid}")
private String email;
```

Then add `validation.email.required=…` to `messages.properties` (and the translations).
The braces form is what triggers `MessageSource` lookup — a literal string stays literal.

Currently migrated (slice 1, the `users` feature): `IGRPUserDTO`, `InviteUserDTO`,
`AddRolesToUserRequestDTO`, `UpdateUserMetadataRequestDTO`, `UserInvitationResponseDTO`,
`ValidateInvitationEmailCommand`, `ValidateInvitationOtpCommand`. Other features still
carry hardcoded English messages; migrate them feature by feature.

For a language field, use the `@SupportedLocale` annotation
(`shared/i18n/SupportedLocale.java`): it accepts `null`/blank and any tag that normalizes
to a platform language, and reports `{validation.locale.unsupported}`.

### Add a report label

`ReportColumnDefinition.of(labelKey, englishLabel, accessor)` carries both a key and an
English default. `ReportRenderer` resolves the key in the requested locale and falls back
to the English label. The header date is formatted with the language's fixed region
(`IgrpLocale.region()`), so `pt` renders `16/07/2026` and `en` renders `16 Jul 2026`.
Cell values and file names stay locale-neutral.

### Add a new platform language

This is a **platform-wide decision**, not a module one: the list must stay identical
across every iGRP module and the Application Center. Adding one means, in this repo:

1. Add the constant to `IgrpLocale` with its base tag and formatting region.
2. Add `messages_<lang>.properties` (it may start partial).
3. Add the file to `TRANSLATIONS` in `MessageBundleConsistencyTest`.
4. Update `validation.locale.unsupported` in every bundle — it spells the list out.
5. Align the Application Center (`src/i18n/config.ts` and `messages/<lang>.json`) and the
   notification service templates, otherwise invitation emails for the new language fall
   back to the module default.

No configuration change is needed for the existing deployments: `igrp.i18n.*` keep
pointing at `en` / `pt`.

## 6. API contracts introduced

### `PUT /api/users/me/locale`

Stores the authenticated user's language preference.

```http
PUT /api/users/me/locale
Content-Type: application/json

{ "locale": "fr" }
```

- `204 No Content` — stored.
- `400 Bad Request`, code `INVALID_LOCALE` — missing, blank or unsupported value.
  Validation happens in the handler (not via Bean Validation) so all three cases produce
  the same error.

The value is normalized to the base tag (`pt-CV` → `pt`) and written to the `locale` key
of the existing `metadata` **jsonb** column of the user table. **No new column** was
added. Every other metadata key is preserved.

It is a separate endpoint rather than a change to `PUT /api/users/me`, which takes a full
`IGRPUserDTO`.

### Reading the preference back

- `GET /api/users/me` already returns `metadata`, so the client reads `metadata.locale`.
- `ClaimsEnrichmentService` still emits `metadata.locale` as the OIDC `locale` claim
  (unchanged).
- `IgrpOidcUserService` seeds `metadata.locale` from the upstream IdP's `locale` claim
  **only when it is not already set** — the IdP must not overwrite the user's own choice
  on every login.

### Invitation locale

- `InviteUserDTO.locale` — optional, `@SupportedLocale`. `POST /api/users/invite`.
- `InvitationDTO.locale` — returned on invitation reads; `null` for invitations created
  before this feature.
- Stored in the new nullable `t_invitation_entity.locale` column (migration
  `V16_1__invitation_locale.sql`, guarded and idempotent, no backfill).

All invitation emails — invite, resend, OTP, cancellation, response — are requested in
the invitation's locale. When it is `null` (pre-i18n invitations), the sender falls back
to `igrp.notification.service.invitation.default-locale`.

On acceptance, `RespondUserInvitationCommandHandler` copies the invitation locale into the
new user's `metadata.locale`. A brand-new user and a `TEMPORARY` account (whose metadata
only holds IdP-derived values) always take it; an already-activated account keeps a valid
stored preference.

### Notification-service retry

The notification service matches templates by **exact** locale and has no fallback of its
own. When it answers `422` with error code `TEMPLATE_ERROR` and a message containing
`No PUBLISHED template`, `InvitationNotificationSender` retries **once** with the API
module default (`igrp.i18n.default-locale`, `en`) and logs the fallback at INFO. If the
retry also fails, it falls through to the legacy mail sender as before.

The same `TEMPLATE_ERROR` code is also used for *missing template variables*, which must
not trigger a retry — hence the message-fragment check in
`InvitationNotificationSender.isTemplateMissing`.

## 7. Gotchas

- **Outside a request there is no requested locale.** Async jobs, M2M flows and scheduled
  tasks resolve text against the platform default bound at startup — not the caller's
  language and never the JVM locale.
- **Logs stay English.** `GlobalExceptionHandler` logs the exception *before* localizing,
  so log lines keep the English enum template, which is what operators grep for.
  Localization applies only to the HTTP response body.
- **`always-use-message-format=true` changes quoting.** A value like
  `Department 'X' is inactive` renders as `Department X is inactive` unless written
  `Department ''X'' is inactive`. The consistency test catches stray quotes.
- **`.igrpstudio` metadata does not know about `PUT users/me/locale`.** The endpoint was
  added by hand to `UserController`; `.igrpstudio/users/controllers/` was not updated.
  Regenerating `UserController` from iGRP Studio would drop it. The two DTO descriptors
  *were* updated (`.igrpstudio/shared/dto/InviteUserDTO.json`, `InvitationDTO.json`).
- **`PUT /api/users/{id}/metadata` replaces metadata**, but a stored `locale` is carried
  over when the payload does not mention it, so an admin metadata edit cannot silently
  reset the user's language. An explicit `locale` in the payload still wins.
- **`PUT /api/users/{id}` (and `PUT /api/users/me`) no longer writes `metadata` at all.**
  Metadata is owned by the two endpoints above.
- **`IgrpErrorCode` templates and `messages.properties` must stay in sync.** They are two
  copies of the same English text on purpose (the enum is the seed and the last-resort
  fallback). The consistency test is the guard.

## 8. What's next

This is slice 1 of the plan (infrastructure + the `users` feature). Still open, per
`_specs/i18n/plan.md`:

- one PR per remaining feature (`roles`, `permissions`, `departments`, `applications`,
  `menus`, `files`, `profile`, `settings`), each migrating that feature's DTO validation
  to `{validation.*}` keys;
- completing the `pt` and `fr` bundles as translators become available (no code change
  needed);
- promoting `shared/i18n` to the shared framework (`core-spring-boot`) once the design is
  validated here — the package is deliberately isolated so the move is an import change;
- moving the email locale fallback chain into the notification service, which would make
  the one-shot retry above unnecessary;
- translation keys for code-defined data (menu labels, `@IgrpPermission` descriptions),
  which are still stored/declared in a single language.
